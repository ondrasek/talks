V1 — Git's Object Model and Design Trade-offs

This note's central claim is that Git is not, at its core, a version-control system: it is a content-addressable filesystem with a version-control interface written on top of it, and that distinction explains why the command-line interface feels inconsistent while the data underneath is small and regular. The evidence is the object model itself — four object types (blob, tree, commit, tag), each named by the SHA-1 hash of its own content, so identical content is deduplicated automatically. Because a commit's hash covers its tree and parent hashes, and a tree's hash covers its children, a single commit hash transitively authenticates an entire project state and history — a Merkle DAG. Refs (branches, HEAD) are the one mutable layer: small files holding a hash or a symbolic pointer to another ref. The note walks this bottom-up using Git's own "plumbing" commands (hash-object, write-tree, commit-tree, update-ref) to show that ordinary commands are just "add objects" or "move refs," and traces the origin story — Linus Torvalds writing Git in days in April 2005 after losing free access to BitKeeper — as the source of its speed- and integrity-first, ergonomics-second trade-offs.

The note is equally explicit about what it does not claim. It does not treat Git's interface as well-designed: it cites a peer-reviewed conceptual-design analysis identifying specific violations, such as staging and working versions not being independent of one another. It presents the absence of rename tracking as a deliberate modeling choice — quoting Torvalds directly — rather than a defect, while still naming its practical cost. On the pending SHA-1-to-SHA-256 transition, the note treats the question of timing as explicitly unsettled: Git's own governing document states there is no planned release date for Git 3.0, and the note flags that some secondary sources claiming otherwise conflict with that primary source, without resolving which is right. It similarly frames large-scale mitigations (partial clone, sparse checkout, LFS) as bolt-ons with their own costs, not as evidence the core model scales natively, and treats a contrastive tool (Jujutsu) only as a way to distinguish essential from incidental design choices, not as an endorsement.

V20 — Git's Remote, Fetch, Push, and Pull Mechanics

This note extends the "a repository is objects plus references" model across the network boundary, arguing that fetch and push are that same add-objects-and-move-refs operation performed against a remote, with one genuinely new element: a third ref namespace, refs/remotes/*, that caches the remote's branches locally. A remote is defined as nothing more than a name bound to a URL plus a fetch refspec; clone writes both. The note separates the three verbs cleanly: fetch is the only read, adding objects and moving only refs/remotes/origin/*, touching neither local branches nor the working tree; push is the only write, asking the remote to move its own refs/heads/* subject to a fast-forward rule the remote itself enforces; pull is fetch plus a local integration step. Through direct command reproduction, the note demonstrates that origin/main is a local file, not a live query — git rev-parse origin/main and git ls-remote origin can disagree, and git status's ahead/behind figures, git branch -vv's [ahead N], and even [gone] are all computed from that local cache and therefore lag reality by exactly one fetch. It also works through a documented three-way discrepancy about what pull does by default: Git's glossary calls it an unconditional merge, the manual names --ff-only as the default, and the source code's actual unset behavior is to refuse when branches have diverged, deferring to pull.rebase/pull.ff configuration otherwise — all reproduced as four distinct behavioral cases. Evidence throughout is Git's own pinned-version source and documentation plus first-person command transcripts.

The note explicitly limits itself to one remote and one refspec, excluding multiple remotes, fork/upstream topologies, triangular push workflows, and most wire-protocol detail beyond one summary sentence. It does not claim its own "objects plus refs" framing is complete at the wire level, noting that real transfers also negotiate capabilities and write side-channel state like FETCH_HEAD. It explicitly declines to say whether the merge/rebase refusal on divergence is pedagogically better than a silent default, calling that an open empirical question. It also flags as unsettled how much of the common origin/main confusion is attributable to the remote-tracking rename versus simple staleness — several sources treat these as distinct failure modes, but none apportions them — and whether Git's omission of a last-fetch timestamp from its status reporting is a deliberate design choice or simply unbuilt. The note separately documents, as a correction to its own earlier draft, that a wording choice in Git's manual it had suspected of being stale documentation was in fact a deliberate, recently-added clarification.

V21 — Git remotes, remote-tracking refs, and what fetch, push, and pull do to them

This note explains what Git's fetch, push, and pull commands actually do to objects and references once a remote repository is involved, building on a companion note's claim that a Git repository is nothing but objects plus references and that every command either adds objects or moves references. It argues that a remote is just two configuration values — a name bound to a URL and a fetch refspec — and that the network boundary adds exactly one new thing, a local ref namespace (refs/remotes/*) that caches what the remote last reported rather than the remote itself. Every claim is backed by a quotation from Git's own documentation or source code at a single pinned version, paired with first-person command transcripts run in the same environment: a fresh clone's recorded refspec, fetch leaving local branches and the working tree untouched while moving only remote-tracking refs, a divergent git pull with nothing configured refusing outright, and a --force-with-lease push rejected as "stale info" once the cached value no longer matches the server. The most developed finding concerns git pull: its manual page's stated default (fast-forward-only) and its actual unconfigured behavior (an outright refusal pending configuration) are shown to be distinct, a discrepancy traced through the project's commit history to a deliberate 2021 behavior change and a 2025 documentation clarification that the maintainer reviewed and endorsed as a description of policy rather than mechanism.

The note is explicitly scoped to one remote and one refspec, leaving multiple remotes, fork/upstream triangular workflows, and custom or negative refspecs out of scope by design. It treats the "objects plus references" model as a simplification of the wire protocol, which also negotiates capabilities and shallow or partial transfer boundaries that the note does not otherwise cover. On its most contested point — why the manual and the code describe pull's default differently — it concludes the two are not in error but describe different levels (policy versus mechanism), while flagging one precedence asymmetry between the unconfigured default and an explicit --ff-only flag as genuinely unreconciled. It leaves open whether reported user confusion about origin/main owes more to the ref-renaming behavior or to staleness, since the one large empirical study it found cannot separate the two even in principle, and it marks as explicitly unverified whether Git's refusal-over-silent-merge design for divergent branches is pedagogically preferable to the alternative, noting that no study of that question was located.

V22 — The relocation of version-control centralisation from the data model into policy

This note argues that distributed version control does not eliminate a single point of authority; it removes that point from the data model and leaves it to be rebuilt as policy. The argument rests on separating three independent axes — centralised versus decentralised authority, locking versus merge-based concurrency, and file- versus fileset-oriented units — which the historical lineage (SCCS, RCS, CVS, Subversion, Perforce, BitKeeper, Git) correlates but does not logically require. Some capabilities a central server provided are only enforceable because the server was structural: exclusive locking (traced to RCS's "exclusive responsibility" rule and re-implemented by Subversion's svn lock and Perforce's +l filetype), per-path access control (Subversion's authz file and Perforce's protections table, both server-side tables consulted per command), and paying large-binary storage cost once rather than once per clone. Offline capability is shown to be structural rather than a feature, including a first-hand reproduction in which a Subversion working copy — holding only the pristine text of one checked-out revision — answered status/diff/info/cat with its repository made unreachable, but failed log, blame, update, and commit. Forges (GitHub branch protection) and Radicle's cryptographic quorum are offered as evidence that authority returns as policy once distribution removes it from the data model, and Epic Games' and Unity's documentation corroborate that game studios still rely on Perforce-style exclusive locking for unmergeable binary assets.

The note is explicit about what it does not claim. "Distributed systems cannot offer locking" is true of the data model but not of practice, since Git LFS locking and forge features implement locking as policy at a single authoritative remote — the limit is that policy cannot bind two peers who exchange work directly, not that locking is unavailable. It also flags that "authority is merely a social convention" understates the real cost of relocating authority once branch protection, CI, and identity all live at one forge. Several points are left open rather than resolved: whether centralised systems retain a genuine or merely legacy advantage for large binaries is called contested; Perforce's market-share claim among AAA studios is sourced only to vendor marketing and is marked unverified; the semantics of Git LFS locking were not researched; and the offline reproduction used a renamed, unreachable local repository rather than a genuine network partition, a gap the note states rather than papers over.

V25 — Centralisation relocated from the data model into policy

This note argues that centralised and distributed version control are usually contrasted as a deployment difference — one server versus many copies — when the sharper distinction is structural: a centralised system makes a single point of authority a fact of its data model, while a distributed system removes that fact but not the need for an authoritative copy, so authority returns as a convention that forges now implement as policy. It draws on Raymond's taxonomy to separate three independent variables (centralised/decentralised, locking/merge-before-commit/commit-before-merge, file/fileset-oriented) and traces the lineage from SCCS and RCS's exclusive-locking model through CVS's shift to merge-based collaboration and Subversion's deliberate re-introduction of locking for unmergeable binary content. It documents what only a structural single server could enforce — exclusive locking, per-path access control, and paying binary-history storage once rather than on every clone — and reproduces the offline-versus-connected asymmetry directly: a Subversion working copy holds only the pristine text of one revision, so status and diff work with the repository unreachable while log and blame fail. It then traces how Git, having removed centralisation from the data model, saw it return as policy at forges (GitHub branch protection) and, twenty years earlier, as BitKeeper's licence-mandated metadata server — evidence that BitKeeper's architecture was distributed and only its licence, not its design, was the constraint Git escaped.

The note is explicit about what it does not claim. It does not assert that distributed systems can never approximate locking in practice — only that they cannot enforce it between arbitrary peers talking directly to each other, and it flags Git LFS file locking as a real counter-example whose exact semantics it has not sourced. It treats Perforce's claimed dominance in AAA game development as reported rather than verified, since the only evidence found was vendor marketing and tertiary repetition rather than an independent survey. It also names its own scalar treatment of "authority" as a boundary that does not fit systems with legitimately partitioned per-subtree authority, such as a Perforce depot with delegated sub-protections. Several questions are left open: what Git LFS locking actually guarantees, how the offline contrast behaves under a real network partition rather than a simulated one, whether any centralised system combines per-path access control with offline history, and whether Jujutsu's first-class conflicts change the locking calculus at all.

V26 — Jujutsu as a redesign of Git's user model

The note is explicit about what it does not claim. V28 — Patch-based version control's commutation model

This note lays out the rival to Git's snapshot model: version-control systems (Darcs, and later Pijul) in which the change itself, not the tree state, is the object with a durable identity, and the tree state is derived by applying a set of such changes. Once a change is first-class, the central operation becomes asking whether two changes commute — whether applying them in either order reaches the same state with each retaining "the same meaning" in its new position. Where commutation holds, order carries no information; where it fails, the pair is either dependent or in conflict, and in Darcs's own formalization those are literally the same undefined-commutation fact. Darcs separates a patch into identity, context, and effect, with identity alone invariant under commutation, and builds cherry-picking directly out of the commutation operator rather than treating it as a separate feature. Pijul keeps that algebra but reframes the merge as a categorical pushout — a universal, non-heuristic construction — and replaces Darcs's pairwise-commutation bookkeeping with a materialized graph of labelled line-vertices that acts as a cache of everything already applied. The payoff the note documents on both sides: a change carries the same identity wherever it is applied, so cherry-picking never fragments into content-identical but differently-hashed copies the way Git's rebuilt objects do, and merging can proceed by set difference over patch identities instead of re-diffing two endpoint trees.

The note is explicit about what remains unresolved. Darcs's own FAQ still answers "no" (as of 2012, unchanged through 2026) to whether its exponential-time merge blowup is fixed, and two first-hand practitioner accounts disagree about how often it bites in practice without either being shown wrong. Pijul's claimed complexity advantage over Darcs is asserted by its own author rather than independently benchmarked, and its atomic operations (line insert/delete, file add/delete/rename) are deliberately narrower than Darcs's arbitrary-patch generality — a trade made explicitly for the pushout construction to work. The note also records a live, unresolved dispute over whether patch-level dependency tracking has any value given that it cannot see semantic dependencies between patches, and it notes that the snapshot model retains an affordance patch systems lose: git bisect walks a total order of complete historical states, while Darcs's local, partially-ordered patch log does not reconstruct "the version whoever wrote the bug was actually looking at." The note treats this purely as reference grounding for teaching Git's design by contrast, not as a recommendation to adopt either alternative tool, and flags that neither tool was actually run on the runner that produced it — every behavioral claim rests on project documentation and independent secondary description, not reproduction.

V30 — Patch theory, as implemented by Darcs and Pijul

V31 — the Gitless critique of Git's conceptual design

This note examines research by Santiago Perez De Rosso and Daniel Jackson (MIT) arguing that Git's usability problems are not vague dissatisfaction but demonstrable defects under a specific theory of conceptual design. The theory defines a "concept" as something a user must understand to operate a system, each concept invented to serve a "motivating purpose"; an "operational misfit" occurs when a concept's prescribed behavior fails that purpose in some scenario. Applying five design criteria — Motivation, Coherence, Fulfillment, Non-division, and Decoupling — the authors' 2016 OOPSLA paper (which supersedes an earlier 2013 paper built on a different, rejected set of criteria) identifies seven operational misfits in Git, each traced to a specific concept and to the criterion it violates. For example, the commit concept violates Coherence because it serves two goals — making changes persistent and grouping logically related changes — that pull in opposite directions; the stash violates Motivation because its purpose connects to no genuine version-control need, which the note reads as evidence the stash patches a deeper flaw (branch/working-directory coupling) rather than serving a real requirement. The authors validated the misfits' reality against a large sample of highly-upvoted Stack Overflow questions, then tested a redesign — Gitless — in an 11-participant user study. Gitless eliminates the staging area and generalizes the branch concept (so each branch carries its own working state) to make the stash unnecessary, addressing four of the seven misfits, with net-positive but mixed usability results across six tasks.

The note is explicit about what this work does not establish. The authors themselves decline to claim Gitless is a "better" version control system — only that it better satisfies the purpose-mapping their method evaluates, under controlled, task-specific conditions. Both papers restrict their analysis to local operations, excluding the entire remote/sync surface (origin versus upstream, pull's rebase behavior) that the note flags as a major gap for a collaboration-focused course. The claim that Git's staging area is "inessential" is asserted rather than demonstrated with usage-frequency data, and the note records named practitioners disputing it on purpose grounds — arguing staging serves a logical-commit-grouping need the papers' own concept table already assigns it, so the live disagreement is over visibility, not existence of the purpose. The 11-participant user study's external validity is thin by the authors' own statement (all MIT-affiliated, none self-identified as Git novices, with the "novice" subgroup defined by task-completion clustering rather than prior experience). The note leaves several questions open rather than resolved: whether the Stack Overflow correlation was ever replicated on later data, whether Git's own maintainers considered these findings, why the Gitless project went dormant after 2019, and whether Gitless's branch semantics actually outperform Git's own 2026 autostash-on-checkout feature for real work. The note reports and stress-tests these claims; it does not argue the underlying design questions are settled.

V32 — Git's two families of monorepo scaling fixes

This note argues that Git's object model — content-addressed blobs, trees, and whole-tree-snapshot commits — does not itself degrade with scale; what fails is the layered-on assumption that a client can cheaply hold, transfer, and walk the entire object graph on every operation. From that framing it argues that every production fix for Git at monorepo scale collapses into exactly two families. "Fetch less" (shallow clone, partial clone, sparse checkout) genuinely gives the client an incomplete repository and tells Git so. "Fake completeness" (Microsoft's VFS for Git, Google's Piper/CitC, Meta's Sapling/EdenFS) transfers even less but presents what looks like a full working tree, materialising files on demand through a virtual filesystem — the first over a real Git repository, the other two over non-Git systems built for the purpose. The note supports this with primary-source evidence: Git's own partial-clone design document, controlled clone-time measurements on torvalds/linux comparing full, shallow, blobless and treeless clones, and first-party accounts from Microsoft, Google and Meta of the systems each built. It treats commit-graph, multi-pack-index, and Git LFS as adjacent but distinct from either family: the first two are local lookup accelerators that change nothing about what crosses the network, and LFS addresses blob weight rather than repository structure.

The note is explicit that fetch-less fixes defer cost rather than remove it — a treeless clone costs the server more CPU than a full clone does, and later commands such as git reset --hard become markedly slower — and that partial clone trades Git's offline-completeness for a standing dependency on a remote server. It notes that sparse checkout remains formally experimental even in the Git version it cites, and that fake-completeness systems are largely unavailable outside the companies that built them: EdenFS and Meta's Mononoke server are not publicly supported, and Google's CitC has never been released at all. It flags one contested point — whether VFS for Git is "deprecated" in favor of scalar — as an artefact-dependent question it resolves by checking the live repository rather than repeating the popular claim. Several questions it leaves explicitly open: why Microsoft quietly removed a maintenance-mode notice from VFS for Git's README without public explanation, whether Meta has published timing figures comparable to Microsoft's Windows-repository numbers, and whether a third family of fix beyond the two it identifies might exist. It states plainly that the two-family taxonomy describes the fixes that were actually built, not a proof that no other approach is possible.

V42 — Stacked diffs as a code-review workflow

This note describes stacked diffs: decomposing one logical change into an ordered chain of small changes, each reviewed on its own, where change n+1 builds on the not-yet-merged change n. It establishes that the practice has two independent origins — Meta's Phabricator/Differential, which stored the dependency as explicit revision metadata because the review object rather than a branch carried the change, and Google's Gerrit/Critique change-list model, which never used branch-per-review in the first place. The two lineages arrive at the same shape from opposite directions, and Meta's name for the practice, not Google's earlier use of it, is what escaped into wider industry use once Phabricator was open-sourced. The note grounds the mechanism in a structural fact about Git: a commit records its parents and nothing records its children, so Git cannot on its own know that a branch is stacked on another branch, and every stacking tool closes that gap by keeping a parent record outside the commit graph. It reproduces on a runner (Git 2.55.0, Linux AArch64) the two consequences that follow — a pull request's three-dot diff against trunk pulls in the layer below an unmerged branch, and a plain rebase without --update-refs silently orphans the branches above the one being rebased — and surveys four tools' restack mechanics (native Git's --update-refs, Graphite's gt restack/gt track, Meta's stack-native Sapling, and Jujutsu's automatically-moving bookmarks), plus GitHub's native stacked-pull-request feature that reached public preview on 2026-07-30.

The note explicitly does not argue that a team should or should not stack, and does not re-derive the object-model or rebase mechanics it cites from companion notes. It flags several open questions rather than settling them: no controlled study compares review effectiveness or defect detection across stack depths or against an equivalent single large pull request; Graphite's on-disk storage format for its branch-parent metadata is undocumented; adoption of git rebase --update-refs since 2022 is untracked; and whether forges other than GitHub have shipped native stacking is unestablished. It treats the dispute over whether stacking improves review quality or only review ergonomics as unresolved, noting that the vendor's defect-rate figures and the counter-argument that "bugs live in the seam between layers" measure different quantities and neither refutes the other. It also declines to treat the vault's separate evidence on small-batch delivery and trunk-based development as evidence for or against stacking specifically, since none of it measures stack-restack dynamics.

V44 — Continuous Integration and Continuous Delivery

This note distinguishes three practices that are casually collapsed into the single term "CI/CD": continuous integration (developers merging into a shared mainline at least daily, verified by a self-testing automated build), continuous delivery (keeping an artefact releasable to production at any time — a capability), and continuous deployment (a policy under which every change that passes the pipeline is released automatically, with no human gate). It traces each practice to a distinct origin — continuous integration to Kent Beck's Extreme Programming in the 1990s, the deployment pipeline to a 2006 ThoughtWorks conference paper, and the canonical treatment to Humble and Farley's 2010 book — and argues the three form a dependency chain, deployment requiring delivery, which in turn requires integration. Drawing on Fowler's and Humble's own writing, it cites an operational three-question test for genuine CI (daily trunk pushes, a test run on every commit, builds fixed within roughly ten minutes) and reports that fewer than 20% of teams who believe they practice CI actually pass it. It documents the deployment pipeline's staged structure — a fast commit stage held to a five-to-ten-minute budget, followed by slower acceptance and release stages — the build-once-promote-the-artefact discipline, and two supporting techniques: feature flags to decouple deploying code from releasing a feature, and the expand/migrate/contract pattern for backward-compatible database schema changes. It backs these claims with large-scale empirical case studies of Facebook's web and mobile release processes and Google's test infrastructure, concluding that deployment frequency itself does not directly cause higher productivity or quality, but the automation that higher frequency forces does.

The note does not claim continuous deployment suits every team. It frames the choice between delivery (a human decides when to release) and deployment (the pipeline's pass is the release decision) as a business decision rather than a technical one, and it names cases — mobile app-store review, embedded and firmware hardware constraints, certified domains such as avionics (DO-178C) and medical devices (IEC 62304), and on-premise or air-gapped distribution — where continuous deployment costs more than it is worth, while continuous integration itself remains largely unaffected. Several points are explicitly flagged as inference or unsettled rather than established fact: the "stop the line" phrase is identified as a Lean/Toyota borrowing rather than a verbatim CI/CD coinage; the IEC 62304/FDA compliance claims and the app-store review-latency figures are marked as reported, resting on a vendor guide and an agency blog respectively rather than a primary standard or first-party statement, and the note's own grounding-gap section names these as open items needing better sourcing. It also leaves an internal tension unresolved between two of its own sources on whether feature flags are a precondition of trunk-based development or only become necessary once a team practices continuous deployment, and it does not verify certain terminology — Humble and Farley's "fan-in/fan-out" pipeline vocabulary, and Kent Beck's own primary-source wording for daily mainline integration — against the original texts.

V45 — Continuous Integration and Continuous Delivery

This note argues that "CI/CD" compresses three distinct, historically separate practices into one initialism, and that the conflation is why a student can run a pipeline daily and still not say what would have to change for their team to deploy on demand. Continuous integration (Kent Beck, Extreme Programming, 1990s) is a property of how a team uses version control — merging to trunk at least daily behind a self-testing build; continuous delivery is a property of the pipeline's artefact — any passing commit could go to production; continuous deployment is the policy that removes the human gate, so passing the pipeline is the release decision. Each depends on the one before it. The claims rest almost entirely on primary sources — Fowler's own articles and bliki entries, and Humble and Farley's book and companion site — quoting Fowler's definitions verbatim and Humble's three-question operational test for whether a team is actually doing CI, alongside his reported finding that fewer than 20% of teams who think they are doing CI can pass it. The note then works through the pipeline's mechanics (commit-stage time budget, build-once-and-promote, stop-the-line) and five "enablers" — trunk-based development, test automation, feature flags, backward-compatible database migration via expand/migrate/contract, and infrastructure as code — each illustrated with named organisations (Facebook web and mobile, Google's Test Automation Platform, OANDA) and worked examples, including a GitHub Actions pipeline and a column-splitting SQL migration.

The note does not claim CI/CD is universally appropriate. Fowler's own precondition — a committed, full-time team — excludes sparse-contributor open-source projects, and continuous deployment specifically is contrasted with release trains and versioned release branches for mobile app-store review queues, embedded hardware constraints, and regulated domains such as avionics (DO-178C) and medical devices (IEC 62304), where it argues the realistic pattern is continuous delivery with a human-authorised, evidenced release gate rather than full automation. It does not claim deployment frequency itself drives productivity or quality, citing Facebook's mobile study for the causally inverted reading instead. Several claims are flagged as inference or reported rather than verified: the "stop the line" phrase's Lean/Toyota origin, the IEC 62304 and DO-178C material (drawn from low-credibility sources not read in full, logged as open grounding gaps), and the Jenkins-as-pipeline Technology Radar verdict, which the note itself calls stale and advocacy-adjacent. It defers the DORA framework's own methodological limits to a sibling note rather than adjudicating them here.

V46 — DORA's five software delivery performance metrics

This note documents DORA Metrics, the empirically validated set of software delivery performance indicators maintained by Google Cloud's DevOps Research and Assessment (DORA) program, which grew out of Puppet's State of DevOps survey (2013) and was acquired by Google, per DORA's own announcement, in December 2018. V48 — The limitations of DORA metrics for measuring AI-assisted software development

This note argues that the DORA delivery metrics (Deployment Frequency, Lead Time for Changes, Change Failure Rate, Failed Deployment Recovery Time, and Deployment Rework Rate) reveal a persistent paradox when applied to AI-assisted development: AI speeds up individual tasks while organizational delivery stability degrades. Google's 2024 DORA Report found AI adoption negatively associated with both throughput and stability; the 2025 report reversed the throughput finding to positive while the negative relationship with stability persisted. The note's central, repeatedly corroborated thesis is that "AI doesn't fix a team; it amplifies what's already there" — organizations with mature DevOps practices convert AI gains into real delivery improvement, while fragmented ones accelerate technical debt and instability. This amplifier finding is independently reproduced, in similar or identical language, by Sonar's 2026 developer survey and Perforce's 2026 State of DevOps Report. The note also triangulates across independent measurement methods — DORA's self-report survey, CircleCI's telemetry from 28+ million CI workflows (showing main-branch success rates at a five-year low), and DX's organizational PR-throughput analysis of 400+ companies (a modest 7.76% median gain) — to argue that real productivity gains are real but far more modest than vendor claims, because the bottleneck has shifted from writing code to reviewing, verifying, and integrating it (the "verification tax"). It further documents measurable code-quality degradation (GitClear's 2026 study of 623 million commits) and traces the well-known METR finding that AI made experienced developers 19% slower on average, alongside a large gap between perceived and actual productivity impact.

The note is explicit about what remains unsettled rather than resolved. It flags the amplifier thesis itself as difficult to falsify — positive outcomes credit organizational foundation, negative outcomes blame it — and notes that "platform quality" is not independently defined from the outcomes it predicts. It downgrades the METR 19% slowdown figure to only partially verified after a 2026 Bayesian reanalysis showed the estimate's confidence interval spans both large speedups and slowdowns, leaving the direction more likely than the magnitude. It treats the 2024-to-2025 DORA throughput reversal as unable to serve as longitudinal evidence, both because DORA is a repeated cross-section rather than a panel study and because the two years used different effect-size units (percentage-per-adoption-increment versus standardized effects) without DORA foregrounding the change. It is agnostic on long-term (3–5 year) equilibrium effects, on whether instability is an inherent consequence of higher change velocity or specifically a function of applying AI to mature/legacy codebases (a competing, explicitly unproven conjecture from a 2026 cross-disciplinary review), and on whether the "J-curve" recovery trajectory DORA proposes actually holds as tooling generations change. The note treats several cited industry sources (Sonar, GitClear, Perforce) as commercially interested and grades them accordingly rather than treating their figures as neutral.

V49 — The small batches principle in software delivery

The note is a reading-note summary of Thomas A. Limoncelli's 2016 ACM Queue article "The Small Batches Principle," which argues that software delivery teams should ship work in small, frequent increments rather than accumulating changes into large releases. It traces the principle's origin to lean manufacturing and the Toyota Production System developed by Taiichi Ohno and Eiji Toyoda, where small-batch production emerged as an economic necessity in postwar Japan, and to Shigeo Shingo's SMED methodology, which made small-batch changeovers economically viable by cutting setup cost. Limoncelli's central illustration is a carpenter who inspects work after each cut rather than after finishing every board in a batch, so that a slipped blade is caught at the second piece rather than the tenth — the note treats this as the clearest statement of why smaller units of work bound the cost of any single defect. The note reports three benefits the article claims follow from small batches: reduced risk (easier testing, review, and rollback), reduced waste (shorter feedback loops prevent building features nobody wants), and higher customer satisfaction (fixes and improvements arrive as continuous flow). It also links the principle forward to the Minimum Viable Product and to DORA's empirical research program, including a 2024 finding — attributed to DORA team lead Nathen Harvey — that AI-assisted coding correlates with reduced delivery throughput and stability because it lets developers generate larger batches of code, undermining the discipline Limoncelli described.

The note is explicit that Limoncelli's article itself supplies no primary empirical data: it argues from analogy and from reference to the lean manufacturing literature, and the empirical corroboration it now enjoys (DORA's surveys, the Accelerate book) arrived years after publication. It flags the carpenter analogy as assuming that defects are detectable at each step, which may not hold for software with complex interdependencies or failures that surface only under load. The note also records what the article does not address: how to decompose a large feature into releasable small batches, contexts where large batches may be structurally required (regulatory release windows, hardware coordination), and the possibility that many small changes create their own review and deployment toil. It flags the 2024 DORA finding on AI and batch inflation as a single-year result whose causal mechanism is plausible but unreplicated, with confounders — team growth, generated code volume, review bottlenecks — not ruled out. The note takes no further position on the article's arguments and does not claim the principle applies equally to every delivery context, noting that regulated or safety-critical software may be a nuanced exception.

V50 — Copy-on-write as a cross-scale sharing mechanism

This note's claim is that copy-on-write (CoW) is a single three-step protocol — share a physical unit between two or more logical owners, protect it so writes are interceptable, and copy only the unit a write actually touches — that recurs, unchanged in structure, across fork()'s anonymous pages, shared-library/DLL mappings, filesystem snapshots, database MVCC row versions, and container image layers, with only the unit of sharing and the arbiter that enforces protection varying between instances. The evidence is a mix of teaching-lab implementation material (Duke's and KU Leuven's copy-on-write fork exercises) for the fault-handler mechanics, vendor and kernel reference documentation (Linux /proc, mmap(2), Windows memory-protection constants, ReFS, overlayfs) for how each instance is parameterised on each platform, and production engineering accounts (Redis, Instagram/Meta's CPython work, Docker) for the mechanism's real-world cost. Built on top of that unification, the note argues that the same protocol has a predictable failure mode it calls the "write storm": because the trap fires per unit on first write, a workload that only looks read-heavy — a GC mark phase, a refcount increment, a metadata chmod, a snapshot under sustained writes — silently becomes a write-heavy one, and the resulting cost (faults, TLB shootdowns felt by other cores, and copy volume inflated by whatever granularity the platform imposes, such as transparent huge pages) is invisible to any metric that counts bytes written rather than the spread of writes across units. It also treats Windows and Linux as substantively different on process creation (Windows has no supported user-mode fork(), so it gets neither the savings nor the storm from that path) while finding genuine parity between the two platforms on library sharing and filesystem snapshots.

The note is explicit that several claims are inference rather than sourced fact, and flags them under a dedicated "Grounding gap" section rather than citing a near-miss source: the arithmetic that a 512 MiB, stride-1 fork should produce on the order of 131,072 minor faults is presented as something to measure, not a verified figure, because transparent huge pages could invalidate it; the claim that Windows has no supported user-mode fork() is inferred from the absence of such an API in the Windows documentation surveyed and from CPython's Windows multiprocessing behaviour, not from a source stating the negative directly; the claim that no per-process Windows counter exists for TLB-shootdown activity analogous to Linux's /proc/interrupts is called explicitly unverified, since an absence found by searching is weak evidence; and the generalisation that tracing garbage collectors on other runtimes (not just CPython) dirty pages by writing mark bits during collection is stated as unconfirmed against a primary JVM or V8 source. The note does not evaluate whether CoW is a good design choice in the abstract — it presents the trade-off (free reads, expensive divergence) as workload-dependent and leaves the reader to judge fit.

V51 — Code review as a social, comprehension-bound process built on top of Git

This note establishes that code review — the practice of developers other than a change's author inspecting it before it merges — is a social convention invented on top of Git's data model, not a feature of Git itself, and that the "pull request" is only the most recent of four historical answers to the question of what unit gets reviewed. It traces the reviewable unit through four generations: the emailed patch series reviewed on the Linux Kernel Mailing List since 1991; Gerrit's one-commit-per-change model, keyed by a Change-Id, which gives dependent changes a native "Relation Chain"; Phabricator's stacked-diff workflow, where each commit lands independently onto master; and GitHub/GitLab's pull request, whose unit is an entire branch of arbitrary size. The note grounds its central claims in three empirical studies: Bacchelli and Bird's mixed-method study at Microsoft, which found that only 14% of review comments concern defects while knowledge transfer and design improvement dominate; a Google case study of roughly nine million changes showing review at huge scale staying fast (median one reviewer, under four hours' median latency) through strict size and culture norms; and the Cisco/SmartBear study of 2,500 reviews, which measured hard ceilings on review effectiveness — no defects found past 90 minutes or past roughly 400 lines. Its synthesis is that review is a bounded-capacity comprehension task whose dominant output is shared understanding rather than defect-catching, and that review latency behaves as a queue, not a fixed delay, so it compounds as reviewer utilization rises.
